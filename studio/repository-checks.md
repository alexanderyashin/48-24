# Проверки репозитория

Валидатор защищает структуру и происхождение материалов от случайного изменения. Он проверяет формальные записи; решение о художественном каноне, согласие человека и наличие авторских прав остаются за людьми.

## Что проверяется

| Область | Правило |
|---|---|
| Структура | Все обязательные пути из `studio/structure.json` существуют; у каждой версионируемой папки есть `README.md`. |
| Жизненный цикл | Каждый предметный раздел содержит `drafts`, `canon`, `archive`; статусы файлов соответствуют папке. |
| Совместимость | Нет конфликтов регистра, зарезервированных Windows-имён, опасных компонентов пути и символических ссылок. |
| Тексты | Локальные Markdown-ссылки ведут к существующим файлам/папкам; кодовые примеры не рассматриваются как ссылки. |
| Метаданные | У содержательного Markdown-файла в жизненном цикле есть обязательные поля. Пара `id` + `version` не дублируется. |
| Канон | Есть запись решения с двумя различными соавторами, датами, доказательствами и хешем точного содержимого. |
| Архив | Указаны причина и преемник; при сравнении с базой архив нельзя незаметно переписать или удалить. |
| Ассеты | Приложен JSON о происхождении и правах; хеш совпадает; нерешённые права не считаются разрешением публикации. |
| Размер и секреты | Отдельный файл до 20 MiB; блокируются известные формы GitHub-токенов, приватных ключей и файлов `.env`. |

Проверка ссылок не проверяет доступность внешних сайтов и корректность Markdown-якорей. Проверка секретов не заменяет человеческий просмотр перед публичной публикацией. Текстовый Git LFS pointer не означает, что большой оригинал проверен: храните мастер и проверяемую запись о нём по правилам ассетов.

## Запуск

```bash
python3 tools/validate_repo.py --root .
python3 tools/validate_repo.py --root . --base FULL_40_CHARACTER_COMMIT_SHA
python3 -m unittest discover -s tools/tests -p 'test_*.py' -v
```

`--base` принимает полный SHA коммита. Он нужен для обнаружения изменений структуры и архива, которые невозможно увидеть по одному новому снимку. Перед локальной проверкой переноса/удаления сначала проиндексируйте изменения командой `git add -A`. Проверка только читает файлы и Git-историю.

## Метаданные текста

Поддерживается намеренно небольшой поднабор front matter: плоские поля со строками и JSON-массивами. Вложенный YAML, многострочные значения и YAML-якоря не используются.

```yaml
---
id: WORLD-EXAMPLE
title: Название материала
status: draft
version: "0.1.0"
owner: unassigned
updated: "2026-11-19"
source: SPOT-0.1
ai_assistance: Drafted with AI and awaiting human review
reviewers: []
canon_refs: []
supersedes: []
---
```

Обязательны `id`, `title`, `status`, `owner`, `updated`, `source`, `ai_assistance`. В `drafts` допустимы `draft` и `review`; в `canon` — `canonical`; в `archive` — `rejected`, `superseded`, `archived`. Архив дополнительно содержит `archived_reason` и `superseded_by`; если преемника нет, записывается строка `none`.

Один `id` может сохраняться между версиями объекта. Одновременно хранимые версии должны различаться значением `version`; для разных вариантов используются разные идентификаторы или версии. Само перемещение файла не означает утверждения его текста.

## Решение о каноне

Канонический материал указывает `decision_ref: studio/approvals/DECISION-ID.json`. Запись решения содержит:

```json
{
  "id": "DECISION-ID",
  "decision": "approved",
  "scope": ["world/world-bible/canon/example.md"],
  "content_sha256": {
    "world/world-bible/canon/example.md": "SHA256_OF_THE_FINAL_FILE_BYTES"
  },
  "approvals": [
    {"person": "alexanderyashin", "date": "YYYY-MM-DD", "evidence": "Actual review URL or attributable source"},
    {"person": "ivan-konyushkov", "date": "YYYY-MM-DD", "evidence": "Actual review URL or attributable source"}
  ]
}
```

Это образец схемы, а не принятое решение. Участники должны существовать в `studio/team.json` с ролью `coauthor`. ИИ не заполняет одобрение от имени человека. Доказательство указывает на реальное подтверждение; в публичный репозиторий не копируются личные сообщения и чувствительные данные.

Хеш вычисляется после окончательного редактирования файла, включая front matter. Любое изменение байтов требует обновлённого решения. Для бинарного канона решение связывает sidecar, а его поле `sha256` связывает конкретный ассет.

**Формальный JSON не доказывает личность и согласие.** Реальная защита требует человеческого review, прав доступа и обязательных проверок GitHub. Валидатор не может проверить, что человек действительно одобрил указанную ссылку.

## Ассеты

Для `art/concepts/drafts/image.png` нужна соседняя запись `art/concepts/drafts/image.png.asset.json`. Она содержит обязательные поля текста, а также `rights_holder`, `license`, `clearance`, `sha256`. Полезно дополнительно указывать генератор/версию, промпт, входные референсы, авторские правки, внешнее местоположение мастера и разрешение на публикацию.

Разрешённые значения `clearance`: `project-authorized`, `permission-on-file`, `public-domain`, `licensed`. Все они требуют реального основания. Неизвестные или спорные права фиксируются в реестре ссылкой и вопросом; сам чужой файл до разрешения не загружается в публичный репозиторий, включая `drafts` и `archive`.

Любой не-Markdown артефакт в `canon` или `archive`, включая JSON палитры, CSV таблицы и исходный код, также требует sidecar и хеша. В каноне этот sidecar получает собственное одобрение. Sidecar без соответствующего файла отклоняется. CSV-реестры в `drafts` и административных папках могут оставаться простыми таблицами без sidecar; известные форматы медиа требуют запись о правах при любом статусе.

Генерация ИИ сама по себе не подтверждает исключительные авторские права. Поле `rights_holder` описывает фактическую правовую ситуацию, а не создаёт её. Лицензии шрифтов, музыки, фотографий и сторонних компонентов учитываются отдельно.

## Изменение структуры

При сравнении с базовым коммитом нельзя просто удалить обязательный путь, README, канонический или архивный материал, либо переписать архив. Изменение самого `studio/structure.json` также требует миграции.

Новый файл `studio/migrations/MIGRATION-ID.json` содержит `base_sha`, `reason`, `decision_ref` и список `changes` с полями `from` и `to`. Каждый затронутый защищённый путь перечисляется отдельно; `to` должен указывать на существующий файл-преемник. Для изменения контракта допускается запись `from` и `to`, обе равные `studio/structure.json`. Решение в `studio/approvals` одобряет конкретные байты миграции и перечисляет двух соавторов. При проверке с `--base` состав имеющих право одобрять берётся из базового коммита. Изменение набора соавторов в `studio/team.json` также требует миграции, которую одобряют прежние соавторы: новые участники не могут одобрить сами своё добавление в том же PR. Уточнение имени или GitHub-профиля без изменения набора идентификаторов/ролей этим правилом не блокируется.

Новую структуру следует сначала добавить, переместить материалы с сохранением истории, обновить ссылки и реестры, затем удалить прежние места в том же проверяемом PR. Изменять архив при миграции можно лишь с явно записанным основанием; стандартная операция — добавление новой версии.

## Границы CI

GitHub Actions запускает принятый скрипт из базового коммита и новый скрипт из PR. Это мешает случайно убрать проверку одновременно с удалением структуры. Однако участник с возможностью менять workflows, правила ветки или обходить checks способен изменить защиту. Поэтому права на `main`, `CODEOWNERS`, правила review и ограничения обхода настраиваются в GitHub отдельно.

При первом rollout базового скрипта нет. Проверка первоначального дерева и тесты выполняются, но сравнение с прежним контрактом в этот единственный раз отсутствует. Ни наличие workflow, ни локальный PASS не являются доказательством, что GitHub Ruleset уже включён.
